# 从 eval 走到架构

## 起点：eval 需要可信的数据

想给项目做 eval，第一件事不是设计指标，是**得先有过程数据**。模型每一轮到底收到了什么、吐出了什么、工具跑了多久，这些当时全散着：一部分只在终端打印一下就没了，一部分埋在 session 文件里但形状不统一，还有一部分压根没记。

会走到 eval 这一步，是因为看了一批 agent harness 方向的论文之后，整体判断变了：harness 正在从「能力容器」变成「运行时控制系统」——它不只是把工具、记忆、路由组合起来，还要负责故障隔离、错误归因、自适应控制。而控制系统的前提是可观测。所以 trace 不是顺手加的功能，是后面所有事的地基。

但当时对它的定位仍然很轻：一个旁挂的观测设施，记几类事件，不影响主流程。第一版就是这么写的——`Trace` 是个 per-session 实例，`Loop` 构造时接一个 `trace=` 参数，需要记的地方直接调。

这个定位是整件事的第一个误判。它错得很不明显，因为**它确实能跑，也确实记下了数据**。

## 「这不可能」

trace 落地后第一次拿到跨 session 的 usage 全貌，看到的是：**新开 session，第一轮请求的 prompt cache 命中率只有 14%。**

第一反应不是分析，是**「这不可能」**。

因为这件事我事先就知道，而且已经处理过了：system prompt 里内容的顺序会影响缓存复用，稳定的放前面、易变的放后面——时间戳那类东西早就被我压到最末尾了。已经有意识地排过序，怎么可能还是 14%。

真正的原因不是排序没排好——**排序的判断其实是对的**，把时间戳压到 system prompt 最末尾，在 system prompt 内部就是最优解。

错的是我以为 system prompt 就是前缀的全部。实际上整个 system prompt 排在 12.7K token 的工具 schema **前面**，所以「压到 system prompt 最末尾」并不等于「排到整个前缀最后」——时间戳仍然横在工具表前面。它每次新 session 一变，分叉点就断在那儿，**排在它后面的 12709 token 工具 schema 一个都不剩地作废**。这也解释了那两个数字为什么长成那样：system prompt 自己 2586 token 里命中了 2176，而工具 schema 12709 全量 miss。

所以这次暴露的不是"排序没做好"，而是一个更基础的欠缺：**我对模型侧的了解不够**。当时注意力一直在自己写的那段提示词上，没有把「一次请求最终被拼成什么结构、各部分谁前谁后」当成一个需要弄清楚的对象。而缓存这类行为恰恰完全由那个结构决定——**从数据传过去的结构本身就能看出很多问题**，前提是你得先把它当回事。

结论因此变了性质：这不是"再排一次序"能解决的，而是**这块内容根本不该在 system prompt 里**。

> 在能测之前，一切关于缓存的讨论都是猜。我猜的方向不算离谱，但没测就动手排序，等于在一个够不着断点的层级上优化了很久。

## 修不动：一条依赖链，其实是个环

把时间戳移出 system prompt，听起来是改一个文件的事。真动手才发现动不了。

会变的内容移出去之后得有地方去。去处是 attachment——每轮随用户输入送达，不进 system prompt。但要让 prompt 分块知道自己走哪条路，就得在注册时声明类型，而**这个决定权在谁手里**从来没被明确过：`Prompt` 是在 `Agent.__init__` 里构造的，system prompt 是 Agent 自己拼的。

于是撞上第一堵墙：`agents` 在模块 import 期就构造完了，那时 `session` 还不存在，而 attachment 挂在 session 上。

墙后面还有一堵：`Session` 构造时需要 main agent 的 system_prompt 当参数。

也就是说——prompt 要等 agent，attachment 要等 session，session 又要等 prompt。**这不是一条依赖链，是一个环。**

到这里，问题已经不在 prompt 模块内部了。

## 撞上的东西原来都有名字

顺着这个环往下拆，拆出来的东西超出了缓存这条线，而且**到处都是**——往任何一个角落多看一眼，都能找到"这里也不对"。

这种"哪里都该修"的体感本身有个正经名字：**Big Ball of Mud**（Brian Foote & Joseph Yoder，1997）。这个反模式描述的不是"运气不好碰上几段烂代码"，而是**系统里从来没有真正被强制执行过的模块边界**，所以耦合都是随手打的补丁，违规密度自然处处都高。知道这个名字的价值在于：它把「我是不是太挑剔了」这个疑问关掉了——体感是准确的，不是错觉。

具体拆出来的是四类，它们看着分散在不同模块，其实是同一个毛病的不同长相：

**一、朋友的朋友（迪米特法则）。** 代码里到处是 `session.attachment.xxx` 这种两级穿透——外部模块拿到 `Session`，然后直接伸进它内部的 `Attachment` 上调方法。同类的还有 `Loop._close_round` 直接 `session.round += 1`。代价不在当下——当下它工作得很好——在以后：`Attachment` 想加锁、想换存储结构、想改状态机字段名，就得同时改五六个分散在完全不同模块里的调用点，漏一处没有任何机制会提醒。`Session` 本该是这个能力对外的唯一入口，而它形同虚设。

**二、缓存放错了地方。** `Agent` 持有一份 `tool_list`，是构造期的快照。工具在运行时会增减（MCP server 连上或断开），所以必须手动调 `refresh_tool_list()` 同步。**这个方法本身的存在，就是"缓存放错了地方"的直接代价证明**——忘了调就永远用旧表，而且不报错。同样的模式已经被复制到了第二处（subagent），不收口还会继续扩散。

**三、横切关注点没有承载物。** trace 要覆盖 Loop、attachment、subagent 三处，可它是个 per-session 实例，只能靠构造参数一层层传下去。传得到的地方能记，传不到的地方就记不了——`agents` 在 import 期构造，那时 session 还不存在，于是 agent 侧的记录只能靠"事后回填"这种别扭做法。**一个横切关注点如果只能靠传参抵达，那它到不了的地方就是观测盲区，而盲区在哪儿取决于装配顺序，不取决于设计。**

这里还分出一个更细的区别，是后来才想清楚的：所谓"信息要能到处流通"其实混装了两件不相干的事——**可达性**（谁能够到谁，本质是依赖注入和对象图的问题）和**谱系**（记录是什么、归谁、活多久、怎么被重放）。hook 是可达性的正当载体，却是**差的谱系载体**，因为 hook 是一个调用点，它自己没有寿命。把这两件事分开之后，"从任何地方写 trace"立刻变便宜了，而且不需要先决定"记录的家在哪"。

**四、装配、持有、触发混在一起。** `Hooks` 本该只管注册和触发，实际上被到处 `hooks.xxx = xxx` 挂满了属性——触发点需要什么就往它身上塞什么。更隐蔽的是：已经写出来的那些 hook 看起来是"通过 hook 通信"，其实**全都隐式依赖"触发的那个实例已经持有了要传的东西"**。`Loop` 持有了 session、memory、hooks、agents，所以它触发时传参传得很自然。那不是通信机制在起作用，是持有关系在起作用，hook 只是借了个道。这一条是这次最反直觉的发现：我以为自己已经有了一套通信设施，其实一直在用持有关系冒充它。

真要让 hook 成为信息通道，正规做法是有一个专门承载共享对象的东西，由**组合根**按依赖顺序一次性构造好交给它，而 `Hooks` 只保留触发与注册。另一条路是把一切都挂到 `hooks` 身上、让 `trigger()` 零参数调用——那叫 **Service Locator**，能 work，但代价是依赖从显式变成隐式，和项目自己定的"优先避免实例级全局耦合"直接冲突。这条路留了个口子（`hook_core` 里那行 `hooks.hooks = hooks`），但没有走。

还有一条属于同一类、却最容易被当成小事的：`session_id` 由 `Session` 自己生成，而 trace 和 log 都要拿它当锚点，于是两个本来和 Session 平行的子系统被迫排队等它构造完。**这条构造顺序依赖是人为造出来的**——三者只是恰好需要同一个 ID，本可以在组合根生成一次、分发下去。

## 一个问题带出一片：yak shaving 和它的停止规则

看见这四类之后，做的第一个决定是错的：**想一次全改掉。**

结果是几十个文件同时处在半改状态，每动一处就牵出新的一处，进度肉眼可见地停住了。

这个经历也有名字：**yak shaving**——为了做 A，发现得先做 B，做 B 又发现得先做 C，一路顺藤摸瓜，原来想干的事反而排到最后。从"把时间戳移出 system prompt"追到"prompt 归属"追到"装配顺序"追到"`_close_round` 直接改 `session.round`"，是教科书式的一条。这本身不是失败，是探索阶段正常的副产品；**但不设停止规则就会没完没了**。

停止规则不是"忍住不修"，而是换一个划界依据：**修复的边界不该是"这条原则被违反的地方"，而应该是"这次改动的爆破半径"**。`_close_round` 那个违规和"把会变的内容移出 system prompt"没有调用链交集，不在这次的半径里，它的正确归宿是**记成 issue，不是现在修**。

同一件事在业界有好几个说法互相印证：

- **Boy Scout Rule**——经手的代码顺手清干净，没经手的不主动去找。
- **Strangler Fig**——遗留结构靠"新代码逐步蚕食"活下来，不是一次性推翻重来。
- **piecemeal growth**——这是命名"大泥球"那篇论文自己给的药：系统在**任何时刻都必须保持可运行**，新的正确结构一小块一小块长出来，旧的一小块一小块被蚕食。

还有一条更锋利的，是 Martin Fowler 对"重构"这个词的原始定义：**每一步都很小、每一步都能验证、每一步都能独立提交**。三条丢了任何一条，做的就不再是重构，而是一次**没有检查点的大重写**。而"从头重写几乎总是灾难"这件事，Joel Spolsky 专门写过一篇（*Things You Should Never Do*），理由和当时的感受一模一样：旧代码里那些看起来蠢的东西，其实各自都在悄悄扛着你没意识到的边界情况，你一边拆一边发现"这里也不对、那里也不对"，永远看不到头。

`git status` 里那一长串几乎覆盖所有模块的未提交改动，就是"安全边界丢了"最直接的证据。不是因为改得到处都是所以失败，是因为这次改动**从一开始就没有被切成可独立跑、独立验证、独立提交的小块**，所以它自然会一路膨胀到吃掉整个项目。

顺带记一条同类陷阱：中途冒出过"干脆全项目普查一遍，看看到底有多少处违规"的念头。那其实是**另一种 yak shaving**——把"焦虑地搞清楚有多可怕"包装成"在做正事"。不管数出来是 20 还是 200，能同时改的量都一样多。

## 把范围收回来

救回这件事的不是任何一个技术判断，是一个**范围判断**：这一轮只做 trace 和 cache，别的记下来不动。

具体的取舍是砍掉 agent 侧的 `agent_profile` 追踪——那是一整套记录 agent 配置变更的机制，写得不算差，但它服务的是"观测 agent 画像"，而当前主线是缓存。删掉它，这一轮就不再需要"trace 回填给 agent"，装配顺序里最难缠的一段跟着消失。四类问题里剩下的三类，全部转成 issue 记录在案，代码不动。

问的问题也从"怎么让现在这一整坨都自洽"换成了：**这堆已改动的文件里，最小的哪一个子集，只要它自己内部自洽，就能让项目重新跑起来？**

> 这一段是整条链路里最值钱的部分，但它写出来一点也不精彩：没有巧妙的设计，只有"这些先不做"。

## 最后落地的东西，和它的代价

- **prompt 分流**：注册时声明 `type`。`static` 拼进 system prompt；`notification` 不进，按 `target` 投给指定 agent。时间戳、timeline、用户画像、技能清单四块因此离开 system prompt。
- **attachment 重写**：新增定向投递（`attachment_target`），生命周期从"用完清空"改成 waiting / processing / finished / miss 四态——因为"渲染进消息"和"确认送达"不是同一件事，中途失败时不能简单退回重投。
- **投递点位进 hook**：`before_session/game_begin` 生产，`before_loop/loop_run` 消费，Loop 不再自己拼 attachment。
- **Trace 改类级单例**，带 pending 缓冲：构造之前发出的记录先入缓冲，落地时吸收。横切关注点终于不用靠传参抵达。
- **`loop_run` / `run_loop` 合并**成单一入口，`source` 参数统一记"谁把消息送进来的"，与 trace 的 source 共用一套词汇。

代价也记一笔。`Trace` 全局化解决了"到不了"的问题，同时**拆掉了它的可测性**：原来工具侧的 trace 探针靠 `Loop(trace=FakeTrace())` 注入假对象来断言，全局单例之后这个注入口没有了，那个探针直接失效。这是一次实打实的交换——用可达性换可测性，当时并没有意识到自己在换，是收口跑测试时才看见的。

## 收口时的最后一个转弯

这条链路本以为到这里就结束了：修复后新 session 首轮命中率 14.2% → 99.3%，两组独立样本，数字是真的。

收口时才发现，`before_loop` 钩子读的入参键名和 `Loop` 触发时传的对不上——钩子每次都在第一个判空处返回，**attachment 从头到尾就没有被渲染过**。它没有报任何错：同步钩子的异常在 `hook_core` 里被 `print` 吞掉，而这里连异常都没有，是一个安静的提前返回。

也就是说，99.3% 全部来自"时间戳离开 system prompt"这一半，而"改走 attachment 投递"那一半当时是断的。数字对了，因果链却接错了一截，而且**差一点就这么提交了**。

这是整条路走完之后最该留下的一条：**验证了指标，不等于验证了机制。** 一个只看指标的验收，恰好会在"结果对了但路径错了"这种情况下给出通过——而这种情况在改动跨了好几个模块的时候一点也不罕见。相应地，收口时补的那条探针不是断言命中率，而是断言"trace 里必须出现 `source=attachment` 的记录"：先证明这条路是通的，再谈它的效果。

修完之后重新采了两个新 session 的数据，结果比预期好，而且**又推翻了一个判断**。当时的预判是：attachment 里那约 1752 token 的内容进入首轮之后，命中率会被长期拉低到 85% 上下。实测第一个 session 是 89.5%（`prompt_tokens` 16600、miss 1752），第二个 session 就回到了 **99.5%**（同样 16600、miss 只剩 88）。

预判错在把"这次是新内容"直接当成了"每次都是新内容"。attachment 携带的内容自己也会被缓存——它只在变化之后的第一个 session 付一次代价，之后整块复用。而且第一个 session 的命中数 `14848`，和 attachment 还断着时测到的那次一模一样：那是 `tools` schema 加 system prompt 那段稳定前缀，新增内容全部落在它**之后**，一点没污染它。

所以最终形态是：请求里的内容比修复前多了约 1752 token，命中率反而从 14.2% 到了 99.5%。这也回过头解释了 `notification` 分块为什么要按"稳定 → 易变"共用一条 order 轴——skill(20)、timeline(30)、memory(35)、时间戳(50)，时间戳被推到整个请求前缀的最末端，它一变只影响它自己。

## 引申出来的 issue 类型

这条链路上发现、但明确不在本次爆破半径内的东西，全部转成了 issue。按类型看，它们分成三组——**类型比具体编号更值得记，因为编号会关闭，类型会重复出现**：

**边界类**（`tech-debt` + `boundary-violation`）。对象跨越自身边界，直接读写另一个对象的内部状态：两级穿透去调内部组件的方法、从外部直接改别人的计数器、把本该属于工具表的快照挂在 Agent 身上。这类问题的共同特征是**当下完全正常，代价全在以后**，而且不会有任何机制提醒你漏改了哪一处。`boundary-violation` 这个标签就是这一轮新加的——它们混在普通技术债里会看不见，因为普通技术债是"写得不够好"，这类是"边界画错了"。

**构造顺序类**（`tech-debt`）。人为造出来的先后依赖：几个本来平行的子系统，只因为恰好共用一个标识，就被迫排成一队，把组合根的顺序锁死了一截。这类问题的识别信号是"为什么 A 一定要等 B"——如果答案只是"因为 B 那儿正好有个值"，那就是它。

**验证类**（`eval-require`）。需要实测数据才能定论、不能靠推理收口的判断。这一轮留下的那条尤其典型：它原本要比"attachment 拼在用户消息前 vs 后"的差异，而收口时发现此前根本不存在可比的两端，**它的前提本身被推翻了**，验证方案得重做。

还有几条尚未立项、但同属这条链路的尾巴：`HookDef` 上新增的 `priority` / `order` 存了却从没排序过（同一点位挂第二个钩子时才会踩到）；同步钩子的异常被 `print` 吞掉，钩子内部出问题不会有任何人被通知——这次的静默失效正是从这里溜过去的；以及承载共享对象的那个东西还没有，`Hooks` 仍然身兼装配、持有与触发三职。
