## 起点：被推翻的不是实现，是前提

plan 这套东西是能跑的。`PlanRunner` 逐 step 驱动模型，`Plan.advance()` 锁定本轮唯一可更新的 step，无进展时熔断——每一条卡控单独看都成立，而且都是为了解决一个真实发生过的问题（模型跳步、模型不肯收尾、模型把后面几步一起标完）。

问题恰恰在这里：**这些卡控共享同一个前提——编排的正确形态是「代码驱动模型」**。整套机制是这个前提的忠实实现，所以它内部越自洽，就越把前提锁得越死。而前提本身从来没有被当成一个可以被检验的对象。

会去检验它，是因为上一轮把 trace 融进项目之后（见 [从 eval 走到架构](eval-to-architecture.md)），「harness 该以多大力度分控与管控模型」这件事第一次有了可观测的依据。有了依据之后再回头看 plan，看到的不是「这里可以优化」，而是**方向反了**：每当模型偏离一次，代码就得多加一道卡控去接住它，而卡控本身会持续增殖。换成一个计划文件加一个更新工具、把编排以可读可写的状态交给模型自己驱动，覆盖的场景更多，出错时的退路也更宽。

所以这一片从一开始就不是重构，是**减法**。这个定性影响了后面每一个决定。

## 第一个被撤回的判断：基线先行

最初定的顺序是：**先立一套 trace 骨架回归夹具当基线，再动手删**。理由听起来很硬——重构完之后模型行为变了一点，没有基线就无法区分是改动导致的还是模型今天心情不同。这条在[上一次复盘](eval-to-architecture.md)里刚刚被总结成「验证了指标，不等于验证了机制」，它的对偶就是「没有基线，就没有『机制没变』这个断言可用」。

这条判断在这一片上是错的，而且错在一个很容易忽略的地方：**回归基线的用途是证明「我没有意外改变行为」，而这一片就是要故意改变行为。** 基线只会全红，红了也说明不了任何事。

更实际的一点是：这时候采的基线里带着 plan 的骨头，plan 一删这份基线就作废，白采。

撤回之后顺序变成：先删，删完再采基线——那时链路才干净，采出来的形状才是真正想固定下来的东西。这个顺序调整的代价是这一片没有等价性证明可用，收益是不用先造一套马上要扔的夹具。**替代的验收不是「什么都没变」，是两条方向相反的断言：该消失的确实消失了，不该消失的一条没少。**

## 「剥离」和「淘汰」是两件事

中途有过一次框架层面的替换。

最初的理解是把 plan 从 `Loop` 里**剥离**出去——毕竟 `PlanRunner` 本来就是独立的一层，`loop_run` 里只有一次无条件调用，看起来是个搬家问题。按这个框架，方案会长成「把 plan 挪到引擎外面，继续用」。

实际定下来的是**整体淘汰**：机制从运行链路上消失，代码交给 git 历史。

这两个词差一个字，但方案的形状完全不同。按剥离做，`Plan` 类、四个工具、plan agent 全都要保留并重新接线，工作量更大，而且保留下来的东西仍然是那个被推翻的前提的实现。按淘汰做，这些全部一次性删除，反而更简单。

**判断动作的性质，比判断动作的范围更靠前。** 范围错了改一改就好，性质错了整个方案都得重来。

## 实际半径：一处比预想轻，一处比预想重

动手前最大的担心是提示词——plan 的指令散在很多地方，手工清一定会漏。

**这一处比预想轻得多。** plan 的模型可见指令绝大部分寄生在四个 `tool_prompt.md` 里，而这些以工具注册表为唯一事实源：全文进 function schema 的 description（`tool/tool_core.py:215`），system prompt 里只有 name 加一句短描述（`get_tool_brief`）。**工具目录一删，两条路径上的提示词自动消失，一个字都不用手工清。** main agent 的身份提示词里根本没出现过 plan。

真正要手工处理的只有一个 agent 身份文件，加两处文案。

**比预想重的是另一处，而且完全不在原来的清单上**：`skill/memory-recall-systematic-test/skill.md` 里写死了 plan 四工具的完整操作流程。它是文档形态，但**属于生产路径**——模型会读到它。不改的话，模型会被这份技能指导去调四个已经不存在的工具，而这不会报任何错，只会得到四次「工具不存在」。

这一条值得单独记：**判断一份 md 该不该改，看的不是它在哪个目录，是模型会不会读到它。** `skill/` 下的文本和 `docs/` 下的文本在这一点上是两种东西。

## 删的时候什么会炸，什么会静默

动手前把「删哪里会怎样」摸了一遍，结果分成很清楚的两类，而两类的危险程度是**反的**。

**会硬崩的只有两处，它们反而是安全的**：

- 只删 `config.SESSION_PLAN_FILE_PATH` 而不动 `session/session_plan.py` → `ImportError` 炸穿 `session` 包，`main.py` 起不来
- 只删 `plan_tool/` 的子目录、留下父 `__init__.py` 里的 `from .plan_design.tool import ...` → `tool/__init__.py` 的 `importlib.import_module` 没有 try/except，`ImportError` 炸穿整个 `tool` 包

这两处会立刻、大声地失败，所以不会漏。

**危险的是静默的那一类**：

- `agents.yaml` 里留着 `plan_tool: true` 而工具没了 → 零报错零日志，授权类别匹配不到任何工具而已
- `PlanRunner` 留着而 `plan_mode_on` 删了 → `session.mode` 永远是 `'auto'`，编排器每轮被调一次然后立即返回 `None`。功能没了，代码还在跑
- agent 身份文件与 yaml 条目不同步 → 双向都静默。`prompt/prompts/agent_prompt/prompt.py` 在文件不存在时直接返回空串，`prompt_core.py` 还把分块级异常吞成一条 `Log.pending_record`

第三条有个现成的活证据：**`memory` agent 现在就没有身份提示词文件**，它一直在跑一份没有身份段的 system prompt，没有任何人发现，因为这条链路不会报错。

结论是：**这条链路天生「静默友好」，删除时不能指望它报错提醒你漏了什么。** 所以验收不能靠「跑起来了」，得靠正面断言。

## 一个被连带删掉、但理由不同的机制

`_tool_calls_api` 里原本每个工具调用前后都 diff 一次 `session.mode`——因为模型可能在一个批次里先调 `plan_mode_off`，后面还跟着三个别的工具调用；相信模型自觉，那三个就会在已经切换的模式下执行。判断依据是**状态的实际变化，不是模型声称做了什么**。

这个机制和 plan 不一样：**plan 是错的，它是对的，只是没有服务对象了。**

所以曾经打算给它留一条重建路径：让工具自己声明「我改变了本轮前提」，引擎只对声明作反应，这样引擎不需要知道任何具体业务。**这个提议也被否掉了**，理由比它自身更重要：那套东西从头到尾只为 plan 存在，把它包装成通用的声明式接口再请回 `Loop`，等于换个名字再污染一次引擎。

真需要拦一个工具的时候，落点在 `Loop` 外面。项目里已经有一条现成但零消费者的路——`pre_toolUse` 钩子声明过 `block` 能力却从没接通（issue #47）。拦截的判据由钩子自己持有，引擎连「有东西被拦了」都不需要知道。

`Session.mode` 本身也一并清掉。它描述的是「模型此刻被允许做什么」，属于对 agent 行为的控制；挂在 `Session` 上，等于把「这次会话是什么」和「模型此刻被允许做什么」混成同一个字段。plan 走后它只剩一个取值——一个恒定字段留在那里，迟早会长回来。

## 测试替不了这一片的班

`test/` 下有七八处和 plan 相关的用例，动手前以为它们是安全网。

实际不是。**它们用的是字符串字面量加假对象，不 import 任何真的 plan 代码**——`FakeSession.mode = 'auto'`、`attachment_target='plan'`、参数化 case 里的 `'plan_design'`。plan 删干净之后，这些用例**照样全绿**。绿灯在这里不证明任何事。

所以这一片新写了一条探针（`test/plan_retirement/test_plan_gone.py`），锁的是正面不变量而不是回归：常驻 agent 名单恰好是那四个、注册表里没有 `plan_` 开头的工具、没有 agent 还持有 `plan_tool` 授权、四个 agent 的 system prompt 都构造得出来且非空、tools schema 干净而 main 的工具表非空。

最后一条是防误删用的。配套的机械核对是工具注册数 **19 → 15**，正好减 4——这个数字比任何断言都直接。

真正的验收是跑一轮真实会话看 trace。第一轮跑完，`source` 全集是 `attachment` / `main` / `system` / `user`，没有 `plan`，也没有 `plan_` 开头的工具名。第二轮里出现了一次并行批次：

```
assistant_output(main) -> calls ['web_fetch', 'web_search']
tool_call -> web_fetch  [success]
tool_call -> web_search [success]
```

这条正好压在改得最多的那段上——原来这个循环每一圈进出都要 diff 一次 `session.mode`，两个调用之间还夹着「上一个切了模式就跳过下一个」的判断。现在两个调用照常跑完、各自拿到结果、协议完整。

## 收口时漏掉的：人读文档一定会漏

按项目规约，改机制要同次核对文档。这一片对了 12 篇：中英两套总览文档、README、CLAUDE.md、配置示例，还把设计叙事那篇改写成了 plan 的纪念碑。做完的时候是当成完成了的。

随后跑了一遍文档漂移检查，抓出**七处漏网**，全是同一个形状：「5 个常驻 Agent」。`README.md` 第 60 行还写着 5，而同一篇的第 161 行已经改成了 4——**一篇文档里前后自相矛盾，读的时候居然没发现**。`docs/ARCHITECTURE.md` 的 213 行和 227 行同样，加上两份英文镜像。还有一处是授权类别的计数：yaml 里的键数从 13 变成 12，「真正有实体工具的类别数」也跟着变了，那句话整段都还是旧的。

这些都不是难判断的地方，就是漏了。原因也不神秘：**逐篇通读靠的是注意力，而计数类断言恰恰是注意力最容易滑过去的东西**——它读起来完全通顺，只有拿去和现场对一遍才会红。

顺带还翻出一条和本次无关的既有漂移：文档说授权类别里只有两个是没有工具挂靠的预留位，实测 `basic_tool` 也是零挂靠，改动之前那句话的算术就已经不对了。

所以这一片留下的最后一条是：**「同次对账」这个规约本身没问题，问题是它默认人会读全。计数类断言必须机械核对，不能靠读。** 这件事已经有现成的入口（文档漂移检查），只是这次先读后查，顺序反了——应该反过来，先让机械核对给出候选，再用人的判断去筛。
