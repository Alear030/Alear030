# ZCode 的记忆系统观察

**中文** · English（暂缺）

← [返回 README](../../README.md) · [文档目录](../index.md)

> **观察对象**：ZCode CLI（智谱 GLM 的编码助手）的跨会话记忆机制
> **观察日期**：2026-09-03 · **被观察版本未记录**——这套机制随时可能已经变了，本文只对观察当日的现场负责
> **状态**：累积式。后续再观察到新的现场会往这里追加。

这是 `docs/` 里第一篇[观察体裁](../index.md#观察)的文档。它不讲 Alear030 是怎么做的，讲**别人家的系统怎么解一个我也在解的问题**。

起因很日常：我用 ZCode 修 Alear030 的 tech-debt issue，聊到一半它提起了上一个会话里的事——哪几个 issue 收口了、哪次重构还没提交。我自己造过一套跨会话记忆，所以第一反应不是「哇好厉害」，是「它把我记成什么样了」。点开文件，看到 frontmatter 的那一刻就基本明白了。

二十分钟后我找到了一个它自己没设防的洞。

**关于证据**：这个体裁没有「以代码为准」可以兜底——被观察系统的源码我看不到。所以本文每条断言都标了证据等级：

| 标记 | 含义 |
|---|---|
| 〔一手〕 | 我在本机文件系统里直接看到的结构或可复现的行为 |
| 〔二手〕 | ZCode 自己对它的机制的说法。**这不构成验证**——模型描述自己的系统提示词时完全可能是幻觉 |
| 〔推断〕 | 我从前两者推出来的，可能错 |

下文凡是二手证据，我都没拿它当结论用。

## 一、怎么看进去的

没有任何特殊手段，全部是本机文件系统里能直接看到的东西。想复现的话：

```
~/.zcode/cli/memories/projects/<bucket>/memory/
├── MEMORY.md            # 索引
└── <name>.md            # 一条记忆一个文件
```

`<bucket>` 是自动生成的，形如 `<目录名>-<十六位十六进制>`。〔一手〕

看到 frontmatter 的瞬间就认出来了：**这是 SKILL.md 的格式**。同一套生态里「配置即注释」的写法是统一的，那么记忆大概率也走同一条路——不是数据库，是一堆带头信息的 Markdown。剩下的问题就只是：谁在什么时候读它们。

这一步没有技术含量，只是**造过一遍的人认得出形状**。后面那些更深的判断才是推出来的。

## 二、审计三问

看任何一套记忆系统，我现在都只问三个问题。这三问是本文真正想交出去的东西——比下面任何一条具体发现都有用：

1. **分层模型**：哪些内容无条件进上下文，哪些按需读？边界在哪？
2. **生成路径**：一条记忆是怎么诞生的——自动抽取，还是模型的手工判断？
3. **纠正传播**：一条记忆被推翻时，引用它的地方会跟着变吗？

三问问完，任何记忆系统都会现出原形。因为它们分别对应三种失败：**上下文预算失控**、**记了不该记的 / 漏了该记的**、**过时结论静默传播**。第三个是最要命的，也是最容易在设计里被跳过的。

## 三、看到的结构

**分层**：`MEMORY.md` 是索引，每条记忆在里面占一行——标题 + 一句钩子 + 指向文件的链接。索引会话开始时自动进上下文；具体的记忆文件只在聊到相关话题时才被读全文。〔一手：索引与文件都在盘上；自动加载这一点是二手 + 行为佐证——它开场就知道上个会话的结论，而我没提〕

**单条记忆的形状**〔一手〕：

```yaml
---
name: <与文件名一致的 slug>
description: <一句话摘要>
metadata:
  node_type: memory
  type: user | feedback | project | reference
  originSessionId: sess_<uuid>
---
```

正文是自由 Markdown，但 `feedback` 和 `project` 两类会额外带两个加粗小节：

- **Why:** 这条为什么值得记
- **How to apply:** 下次该怎么用它

以及内联的 `[[另一条记忆的 name]]` 软链接。**注意 `related` 不是 frontmatter 字段**——关联关系只以正文内联链接的形式存在。〔一手〕

`type` 四类的分工：`user`（用户是谁）、`project`（项目在进行什么）、`feedback`（用户教过的做事方式）、`reference`（外部资源指针）。〔二手，但与盘上文件的实际内容一致〕

**Why / How to apply 这个强制字段是我最欣赏的一处设计。** 只有事实没有用法的记忆，召回时特别容易被机械照搬——把「上次这么做对了」当成「这次也该这么做」。强制写下用法，等于逼着写入方当场想清楚适用边界。

## 四、三处同构

三处我一眼认出来的形状，因为都是我自己造过的：

**1. frontmatter 即 skill 格式。** 记忆和技能共用一套头信息约定，意味着这套系统里「给模型看的结构化文本」只有一种写法。这是省心的选择：少一套格式就少一套解析、少一处漂移。

**2. 索引粗筛 + 按需读全文，是两段式检索的影子。** 我在 Alear030 里做的是「timeline 粗筛 → 语义精排」，这里是「索引钩子命中 → Read 读全文」。区别在于我那层粗筛是代码算的，这里的粗筛是**模型的注意力**——没有 embedding、没有向量库、没有检索接口，索引那几行就是目录，命中了才翻文件。〔结构一手，无向量库为二手 + 目录里确实找不到任何索引/向量文件佐证〕

**3. `originSessionId` 即来源坐标。** 每条记忆带着它诞生的会话 id，这条纪律和我给自己定的「派生数据必须保留来源坐标」是同一条。

但坐标的**精度**不一样，这是第一个真正的差异：它只到会话级，没有轮次。〔一手：字段里就没有 round〕ZCode 说它有一个按 sessionId + 自然语言 query 做语义回溯的工具来弥补〔二手，未验证〕。如果属实，那么两套系统在这里的取舍是清晰对立的：

| | 坐标精度 | 回放方式 |
|---|---|---|
| ZCode | 会话级 | **语义近似**——靠检索在会话里找片段 |
| Alear030 | `(session_id, start_round, end_round)` 轮次级 | **确定性**——坐标即物理身份，直接定位 |

粗坐标 + 语义回放的好处是写入便宜、不怕重编号；代价是回溯结果不可复现。细坐标的代价我也付过——切片模型经常把重喂窗口当成新对话重新编号，得靠偏移量把整批拉回真实轮次（见[记忆系统模块文档](../modules/memory.md)）。

## 五、两处我猜错的地方

按观察体裁的规矩，猜错的过程留在文里。

**错处一：我以为 `user-` 前缀是跨项目层。**

目录里同时有 `alear030-` 开头和 `user-` 开头的文件，我想当然地认为前者是项目绑定的、后者是从项目记忆里提取出来的跨项目记忆。

**不是。整桶都是项目绑定的**，前缀只是 `type` 的命名习惯，不是存储分层。换个项目，记忆是全白的——这套系统根本没有全局记忆桶。〔一手：`memories/` 下只有 `projects/` 一个子目录，没有任何全局层〕

**错处二（在错处一的基础上继续错）：我以为「项目」是分桶的单位。**

不是。**分桶的单位是工作目录。** 本机同时存在三个桶：主仓库 checkout 一个、`Alear030_dev` worktree 一个、无项目会话的默认桶一个。〔一手〕

同一个仓库，因为我用 git worktree 开了第二个工作副本，记忆就裂成了两半——主仓库那个桶里攒下的结论，dev worktree 里的会话一个字都读不到。

这一条对我格外有后果，因为我几乎所有开发都在 worktree 里进行。ZCode 自述的「换个项目就全白」，实际情况是**换个 worktree 就已经全白**。〔一手 + 推断：分桶键含目录名，未验证哈希的具体输入〕

这不是 bug，是「用目录当项目身份」这个简单选择的直接后果——简单，而且对绝大多数不开 worktree 的用户完全够用。

## 六、三个取舍

### 6.1 纠正不沿链接传播

`[[链接]]` 没有反向索引，也没有触发器。〔二手 + 一手佐证：目录里不存在任何反向索引文件〕

所以当一条记忆被推翻时，指向它的其他记忆不会有任何反应。系统提示里（按它自述）规定了单文件维护纪律——发现记错的就删、重复的就合并——但**没有规定传播**。

一个可落地的补丁其实很轻：链接名就是文件名，反向引用可以直接 `rg "\[\[<name>\]\]"` 整个目录搜出来，把「纠正」从一步动作改成「改目标 + 反查引用 + 同步修正」三步。这个补丁在观察当天就写进了它自己的 feedback 记忆里——顺便也演示了 feedback 类记忆是怎么诞生的：**用户当场教了一件事，模型判断值得长期遵守，于是写文件、登记索引。全程手工判断，没有任何自动抽取机制。**〔一手：那条记忆现在就在盘上〕

### 6.2 真正的污染主通道是索引，不是链接

这是我在写这篇的时候才想明白的一层，也是我认为这套设计里最值得说的一处。

上面那个链接补丁防的是**次要通道**。因为：

- `[[链接]]` 指向的记忆，只在模型决定去读它的时候才进上下文；
- 而 `MEMORY.md` 索引是**唯一无条件、每次会话都进上下文的东西**。

规则说索引里每条只留标题和钩子、不放内容。但实际写出来的索引行不是这样——为了让钩子有召回价值，它们塞进了 commit 短哈希、「已拍板」「已收口」这类状态结论、具体的数字。形状大概是这样（示意，非实际内容）：

```markdown
- [某重构进行中](some-refactor.md) — 三处改造已落地并提交至 <短哈希>，未推送；剩下一处待拍板
```

于是索引同时是**信息密度最高**和**最少被复核**的一层：模型读全文时至少会看到 Why / How to apply 里的适用边界，而索引行只有一句斩钉截铁的结论，还每次都自动注入。

**观察当天抓到的一个现场**：索引里有一条记忆断言某篇文档已经落盘、只差提交。我在两个 checkout 里全盘搜索——那个文件不存在，只有一个空目录。无论它是从未写成、还是事后被删，索引都没有跟着变；而在被更正之前，每一个新会话都会把「那篇文档已经存在」当作既成事实读进去。〔一手〕

这正是论文里说的 stale propagation，在一个成熟产品的记忆设计里原样躺着。**无传播治理的记忆系统里，污染是常态而不是异常。**

### 6.3 多个会话并发写同一个桶

同一个桶会被多个并发会话写。〔一手：索引里出现过不是本次会话写入的条目〕

所以 6.1 的传播问题不只是理论风险——它叠加了一个真实的多写者一致性问题：A 会话正在依据某条记忆做判断时，B 会话可能已经把它改了或删了。这里没有看到任何锁或版本机制的痕迹。

## 七、这套设计放在它自己的场景里

上面三条我都写成「取舍」而不是「缺陷」，是认真的。

拆开看，这套东西的本质是**一个约定俗成的目录结构 + 几条写在系统提示里的纪律 + 一个自动加载的索引**，零基础设施：没有向量库、没有检索服务、没有校验器，全靠模型自觉遵守约定。而它确实工作——跨会话记住了正确的事，也确实在被纠正时改掉了记错的东西。

对 ZCode 的使用场景来说，这个精细度是够的。绝大多数用户不会在同一个仓库上开三个 worktree 并发跑会话，也不会攒到让索引撑爆上下文的量。**在会撑爆之前，用户早就换项目了。**

而且它选的这条路和我选的是同一条：拒绝专用基础设施，用「表示 + 纪律」代替。赌的都是**表示和纪律比机器更重要**。上面那些缺口不是这条路走错了，是这条路走到一定规模之后必然要面对的下一批问题。

## 八、和 Alear030 的对照

我自己那套踩过同样的坑，解法列在这里不是为了比高下——是因为**同一个问题的两种解法摆在一起，比任何一种单独讲都清楚**。

| 问题 | ZCode 的选择 | Alear030 的选择 |
|---|---|---|
| 来源坐标精度 | 会话级，回放靠语义检索 | `(session_id, start_round, end_round)` 轮次级，回放确定 |
| 记忆被合并/替换 | 手工删文件 | `merged_from` 记下被吸收的旧维度名，**精确删除**，不靠「缺席即删」的猜测 |
| 重复写入 | 无机制 | 坐标做去重键的**两层去重**：锁外乐观去重省算力，锁内二次去重保正确 |
| 并发写 | 未见锁或版本机制 | **三段式锁**：锁内读快照 → 锁外跑 LLM → 锁内短写；写回按坐标逐片合并而非整表覆盖 |
| 分桶单位 | 工作目录 | 项目 |
| 索引 | 手工维护，条目含实质结论 | 从落盘数据派生 |

最后一行是我事后才意识到最要紧的差别：**手工维护的索引会漂移，派生的索引不会。** 我当初做成派生的理由只是「省事」，现在看它顺手消灭了一整类失效模式。

需要说清楚的是，右边这列也不是白得的——两层去重、三段式锁、坐标归一化，加起来是这套记忆系统里最难写、bug 最多的部分。ZCode 用几行系统提示换掉了这些代码，也就同时换掉了这些保证。**这是一笔明码标价的交易，不是疏忽。**

## 九、仍然开放的问题

- 索引长到什么程度会开始挤占上下文预算？有没有淘汰机制？（观察当天的量还远没到边界）
- 语义回溯工具的实际召回质量如何？〔完全未验证，仅二手〕
- 分桶哈希的输入到底是什么？绝对路径还是别的？换机器、改目录名会怎样？
- 系统提示里那套纪律的原文长什么样？目前所有关于「规则」的描述都只有二手证据。

---

**方法论回到开头那三问**：分层模型、生成路径、纠正传播。这三问是可迁移的——问完任何一套记忆系统，它的上下文预算、它记东西的口味、它烂掉的方式，都会露出来。

我能在二十分钟里问完，不是因为我聪明，是因为这三个坑我自己都掉过。
