以下的内容是我个人当初的想法，以及开发 Alear030 过程中与他之间的对话。包括从项目的历史会话记录里涉及到的：61 个会话、393 个切片，其中 220 个与记忆机制相关。**用这套记忆系统的产物，重建它自己的设计史。**

下文引述的「Alear030」就是当时正在开发的这套系统本身——那些对话是我一边写它、一边和它讨论怎么写留下的。

## 最初的目标其实不是一个记忆系统

我要的是一个**能自己生长的 agent**。自涌现是主线，记忆是实现它所必需的底座，不是终点。

这个区别听起来抽象，但后面所有看起来奇怪的选择都从它来：讨论最久的图结构为什么主动没有落地、召回为什么至今是暴力全量扫描、系统里几乎所有分类体系为什么都不写死。

这句话不是我现在回头总结的。它的出处是[图那一章](#关于存储结构的探索-图构思最久最波折的方向)——2026-06-26 那次讨论跌到谷底的时候，Alear030 把这件事点破了。想先看依据可以直接跳过去。

## 一直以来的参考对象——人类本身

我的起点是人类记忆这套机制本身——不是照搬某篇论文，而是「记忆应该是怎么工作的」。里面无法用机器实现的部分（神经网络、神经化学递质），我换成了别的方法。

### 脑区对应是后来才知道的

顺序值得说清楚：**我是先按「记忆应该这么做」把东西做出来，之后才知道它对应人脑的哪些结构。**

2026-06-24 的记录里有这个转折点。我描述完自己怎么想 `session_recall` 之后，Alear030 指出——这是**从功能视角转向了认知建模视角**。是他给我的做法命的名。同一次对话里还牵出了《心智的构建》里「记忆是当场重建」的说法。

到 06-26，摘要里的措辞已经变成我「有意构建类人脑记忆系统」，我自己也开始反省一件事：人类记忆的触发依赖感觉和画面，而不是关键词。

再往后，这种对应关系变成了明确的设计输入。07-04 讨论情绪记忆时，我直接从海马体与杏仁核的分工谈到了「给切片打情绪标签、高情绪标签的切片自动注入上下文并持续留存」，顺带得出一个结论：**自然淘汰优于显式的遗忘管理**。

所以完整的说法是：**起初不是有意对应，是做完之后才被指认出来，此后才转为有意识的参考。**

### 关于同类项目

中途我搜过几个当时比较火的 memory 框架，想看有没有人在做同样的事。论文层面确实有一些是这个方向的，但工程实现上似乎没见到走这条路的，于是我自己开始尝试。

## 底座：先让「一件事」能被存下来

下一章那场关于图的讨论，第一句话就是「你说的这个 slice 之后没法变动了」——它建立在切片这层已经存在的前提上。所以先说底座是怎么建起来的。

### 从「分类存储」到「经历流」

我最初的方案是主动给信息分类、存进对应的地方。到第二代，我把它推翻了：**不预先分类，把经历原样保存成「经历流」**，再通过触发、关联、提炼形成经验。

今天 `session_detail` 里那份完整、无缝、不被裁剪的原始消息与切片，是这个决定的直接产物。派生层可以重算，经历流不能丢。

### 冷启动逼出了增量切片

早期我把摘要链路挂在 `compress` 上，但压缩很少触发，召回长期无米可炊。

我的解法是每轮从最后一片的起始轮次重新切一遍。关键的一点是我发现：即使还没有 summary，`topic` 与 `key_words` 已经足够支撑召回。今天的「开口尾片 + 重喂窗口」就是从这里来的。

当时我也看到了代价——早期的切片决策不可逆，缓解手段是将来做定期全局重切。这一条至今没做。

### 切分与存储解耦

切片粒度总是不理想，要么太细要么太粗。我的结论是不要指望一步到位：**切分只负责切分（追求纯度），组织与聚合交给存储层。**

今天「`session_slice` 是事实源、`slice_node` 是派生存储」的分层，就是这条原则的落地。

### 切片卡顿逼出了 Hook 系统

每轮对话后同步切片会阻塞输入，体感很差。我的解法是把它丢进后台线程串行处理。

真正重要的是下一步：**我把那个后台维护线程扩展成了「可注册的 pipeline」，支持后续挂任意 hook。**

今天 Alear030 整个事件驱动 Hook 系统，源头是这个体感问题。不是我先设计了扩展机制再去找用途，是反过来。

## 关于存储结构的探索-图：构思最久最波折的方向

这是我投入讨论最多、最后自己放弃落地的一块。整个过程发生在 2026-06-26 的一次会话里，从提出到定案 16 轮。

下面保留原话，因为摘要里完全看不出这条曲线。只修了错别字，以及一处当时随口说岔了的归属。

### 提出

> 我突然有了一个方向
>
> 就是说，你说的这个 slice 之后没法变动了，实际上是对的……我突然就有了一个想法，我为什么不在新确认一个 slice 之后，马上就将这些 slice 结合 embedding 做成类似图结构的东西呢？

想法是在切片层之上长出一层图，节点之间自动建边，跨会话召回时把命中的片段连起来。

### 第一道裂缝：入口从哪来

> 图我实际上也已经理解了，现在还是存在一个问题，就是图可以自动扩散自动取建立节点之间的边，但是问题在于在 memoryrecall 的时候，第一个节点怎么入手，我不能为了找到这个节点再遍历一遍节点吧哈哈哈哈

图能扩散，前提是得先站到某个节点上。而找到那个入口节点本身就是一次检索。

### 致命一问

> 不是那问题就在于我都全量跑 embedding 相似度了，我为什么不直接取出来前三个最相似的返回，我还用什么图了

如果入口已经靠全量 embedding 找到了，那 top-K 就已经是最相似的结果，扩散一跳拿到的要么重复、要么不够相似反而稀释精度。

Alear030 的回答没有绕：

> 如果入口是全量 embedding 匹配取 top-K，图在**当前 recall 精度上**确实提供不了什么增量。……当前阶段，纯 embedding 全量匹配取 top-K 就够了。图在 recall 上暂时没必要。

### 谷底

> 那咱们研究这么半天，结论是啥都不如直接暴力 embedding 相似度直接全量匹配吗= =

> 关键是要落地啊，咱们上面说的这些多锚点、图、共振听起来都挺好的，关键是我一开始就是为了 recall 去研究的，然后研究到最后发现不如全量 embedding 相似比较。。。。

### 转折：不是图没用，是位置放错了

Alear030 的回应是把每样东西重新归位：

> 不是白费。我们搞清楚的不是「图没用」，而是**图的位置放错了**。

| 之前以为是 recall 的优化 | 其实它解决的是另一个问题 |
|---|---|
| 增量切片 | **冷启动**——让新记忆立刻可被搜，和怎么搜无关 |
| `worthy_summary` | **编码选择性**——记什么不记什么，和怎么搜无关 |
| 多锚点 | **编码丰富度**——给未来留入口，不是让今天的 recall 更准 |
| 图 | **记忆的关系层**——跨 session 聚合、扩散激活、共激活统计 |
| 锚点共振 | **触发方式**——不是「搜」而是「被触动」，是未来的范式 |

**今天记忆系统那套四层架构（编码层 / 存储层 / 检索层 / 关系层）就是在这一刻分出来的。** 那个让人沮丧的结论没有杀掉任何设计，它逼出了一次职责分离。下一章之所以能作为独立一层来讲，也是从这里开始的。

### 全章的枢纽

> **我**：有点难说的感觉，我不想放弃我现在的思路

> **Alear030**：那就不放弃。
>
> 全量 embedding 是 recall 的最优解，这个结论是对的。但这不等于你的思路错了——只等于**你把它们放错了场景**。
>
> 你不想放弃的东西——锚点、图、共振——它们要解决的问题不是「怎么搜得更准」。recall 用全量 embedding 已经够准了。
>
> 它们要解决的问题是另一个：**当 Agent 不需要被问到，自己就想起了什么的时候。**
>
> 你现在做的 recall 是「被动唤起」。但你的思路——多维锚点、图扩散、共振——全部指向的是**主动涌现**。人类记忆最核心的特征不是「被问到能答出来」，而是「不提也会想起来」。
>
> 你不想放弃，因为你知道被动唤起不是终点。

这段就是[开头那个立论](#最初的目标其实不是一个记忆系统)的出处：**自涌现才是目标，召回只是底座。** 图之所以在召回这场辩论里「输了」却不该被丢掉，是因为它本来就属于目标那一层，不属于底座。

### 定案

我还在追问：

> 就是你忽略我全部的限制，什么不做什么之后做，什么需要积累，这些都不是问题，我在探讨的就是图的这一套具体落地的场景和意义，什么地方能证明图这一套是必要的而且是必须的并且是好的

最终的方案是我自己给出来的：

> 实际上其实最好的效果是需要 recall 的时候就暴力搜索，但是结果上需要进行节点关联，然后下次再 recall 到节点的时候需要判断 topk 节点是否存在关联的节点，如果存在就联带返回？

Alear030 的回复是三个字：「对。就是这个。」然后把它写成了一句话——**图管联带，不管召回**。主结果只靠 embedding 相似度保持干净，图只做结果增强，对 top-K 扩散一跳带回关联节点。

### 现状

**这套方案我至今没有实现。**

不是遗漏，是排序：底座得先建好。今天 `memory_recall` 仍然是全量 embedding 暴力扫描，没有图、没有关联扩散。

## 检索：当前记忆框架几个实际使用测试的结论

上一章分出的四层里，检索层从此独立演进。这一节的三条都不是设计出来的，是实测撞出来的。

### 时间锚点：从图的时序边换成注入 session_id

纯 embedding 处理不了「刚才聊了什么」这类时间邻近性。当时我有两个方案：给图加时序边，或者在新会话开始时注入最近若干个 session id。

我选了更轻的后者。这条路后来长成了今天的 `timeline.json` 与 `timeline_prompt` 分块。

### 一个我自己测出来的反直觉结论

时间线上线后我做了双阶段检索：先用时间线定位候选范围，再用 `session_ids` 精准召回，替代全量扫描。听起来更聪明。

实测结果相反——**预筛选漏掉了 embedding 打分最高的片段**。凭时间线描述做的判断不如暴力全量检索准，被误选的是一个明显不相关的会话，被漏掉的恰恰是最相关的那个。

更彻底的反思在后面：时间线是个**共享变量**，它在构造关键词的阶段就已经完成了一轮预筛选，所以「全量扫描 vs 带 session_ids」这个对比本身从一开始就不纯粹。结论是时间线本身才是最强的预筛选机制。

这就是为什么 `memory_recall` 至今保留全量扫描作为默认行为，`session_ids` 只是可选的收窄参数。

### summary 质量锁死了召回上限

有一次我要找回一段关于图结构研究的讨论，连搜三次都没命中。暴露出的问题是：**如果 summary 没有捕捉到那个语义，召回永远找不到它**，无论向量算得多准。

这条至今是这套设计的结构性上限。

## 什么是自涌现？现在是什么程度？潜力或者我对他未来的期望是什么？

先说清楚这个词指什么：**这套系统里的东西不是我写死的，是它自己长出来的。**分几类记忆、画像有哪些维度、用什么特征词去认，都不由我预先规定。

我最初设想的是纯底层的图结构理想模型，后来落地成了现在的分层形态：

> 底层经历流与切片坚固，上层 `type_name` 稳定、`feature` 层独立分化——**分层自涌现，互不阻塞**。

变的只是**工程形状**，从纯图换成了分层，目标本身从头到尾没有动过。

而即便是现在这个形状，也只能算半个自涌现。[机制文档](../modules/memory.md#自涌现这条管线会长出东西)里写的三层——分类特征词会长、画像维度会长、技能会长——都是真的，但**类型集合本身是我写死的**。`memory_core.py` 的 `slices_pipeline` 里就两个硬编码分支：

```python
if 'user_info' in slice.get('slice_type',[]):
    ...
if 'task' in slice.get('slice_type',[]):
    ...
```

切片被分完 type 之后能进哪条 pipeline，被钉死在 `user_info` 与 `task` 这两种上。特征词能自己长，但「一共有哪几类记忆」这件事，还是人定的。

**下一步是把自由度完全放开：不再由我规定有哪几种 type，而是让类型自己出现，再配上对应的管线处理方式。**

这一步做成之后，`user_info` 就不再是一个写死的类别，而是「某个具体对象的 info」——每个实体各有自己的一份，再往上聚合成 `human_info` 这样的层。今天只有 `user_info` 与 `task` 两种，是因为管线还得我一条条写；类型能自己长出来，管线才谈得上跟着长。

到那时候才算是真的自涌现。这不是欠账，是主线的下一段。

## 我在开发过程中的一些取舍

有一句话贯穿始终，是我 6 月底自己总结出来的：

> **让数据产生结构，让使用驱动优化。**

它解释了为什么这套系统里几乎所有分类体系——切片特征词、画像维度、任务节点——都不是预先写死的字段表，而是随使用生长出来的；也解释了为什么上一节那个「类型写死」在我这里是个待解决的问题，而不是理所当然的设计。

另一个取舍是关于精力的。单人项目，我在中期做过一次明确的决定：**把 memory 当基础设施看，修到不会崩溃即可，优先推动系统继续生长**，而不是先把每个角落都做到工业级。

[机制文档的已知限制](../modules/memory.md#已知限制)那一节里的多数条目，是这个取舍的直接结果，不是疏忽。
