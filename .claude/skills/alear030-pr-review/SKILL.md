# Alear030 PR review

merge 前对一个已开 PR 的整批改动做审查。**硬边界是严格只读**：不改任何代码、不改 git 状态（add/commit/stash/checkout 都不行）、不跑 `python main.py`。只汇报，处理方式由用户决定。

窗口卡在 `$alear030-push-merge` 两段之间——PR 已开、尚未合并。

## 开工前必读（不要跳过）

`docs/retrospective/eval-to-architecture.md` 的两节：

- **「撞上的东西原来都有名字」**——本项目历史上真实翻过车的四类靶子
- **「引申出来的 issue 类型」**——发现该往哪三类归

必读的理由，复盘自己那句话就是：**类型比具体编号更值得记，因为编号会关闭，类型会重复出现。** 不带着这四类去读 diff，读到的只有「这段代码写得对不对」，读不出「这个边界画错了」。

## 四类靶子：review 时怎么问

定义在复盘里，这里只给提问方式。

1. **边界穿透** —— 这次新增了几处 `a.b.c` 两级穿透？谁从外部改了别人的状态字段？那个对象自己的入口是不是形同虚设？
2. **缓存放错地方** —— 新增的快照或副本，运行时会不会变？变了靠谁同步？出现 `refresh_xxx` 这类手动同步方法，方法本身就是代价证明。
3. **横切关注点的可达性** —— 新增的横切设施靠什么抵达？传参能到的边界在哪？到不了的地方是不是盲区，而盲区位置取决于装配顺序、不取决于设计？如果这次是靠**提升作用域**（类级、进程级、全局单例）换来的可达性，那换掉的是什么——它还能不能被注入替身来测？会不会被构造两次或被并发访问？
4. **装配 / 持有 / 触发混在一起** —— hook 传的那些参数，是真的通过 hook 通信，还是借了触发者的持有关系？换一个触发者还成立吗？

## 三道对账

顺序固定，一道一道过完，不要边读 diff 边随机跳。三道之间无依赖，**可以派 Explore 子代理并行**，子代理同样只读。

**一、数据对账。** 对每一个把数据写到进程外的调用点（落盘、发请求、写外部存储），回答「改动前后各自到底落了什么、发了什么」——不是「代码怎么写的」。看结构本身：字段有没有增删、内容有没有混进新来源、消费端对这个结构的假设还成不成立。**这一道最容易跳过，也最贵**：diff 读得再细，也看不见落盘语义反转。

**这些调用点要你自己列，并且把清单和你的找法一起写进报告。** 本技能刻意不给现成清单——写死的名字会在改名或新增实现之后照样返回结果，让人以为查过了。清单是这一道的交付物，不是准备工作；列不出来就说明这一道还没开始。

取基线不需要动 git 状态：`git merge-base <base 分支> HEAD` 拿到分叉点，再用 `git show <分叉点>:<文件路径>` 读改动前的原文。**不要 checkout、不要 stash**——只读的硬边界在这道对账里同样成立。

**二、声明↔消费对账。** 每一个新增或修改的参数、配置字段、注册声明，找它的消费端。**无人消费即死参数，说明 API 面在撒谎。** 三种形态都要查，漏掉后两种是常见失误：

- 参数被收下却在函数体内从未引用——最容易发现的一种
- 参数被逐层往下传，**在链条中途某一跳被丢掉**。这时它在上游看是「有人消费」，只有走完整条链才看得出断点
- 声明的**取值集合**有没有真的出现在产物里。某个取值被刻意区分出来（注释常会说明它用来区分什么），却从来不出现在任何产物中，说明这条区分是空转的

每条注释宣称的行为也要在机制里找到落点；找不到，就是注释在承诺机制并不具备的能力。**本次 PR 新写下的注释与文档断言排在最前面查**——它们没经过任何时间检验，而写的人读自己的断言读到的是「我刚确立的事实」，只有非作者才会把它读成「一个待检验的声明」，所以这一类恰好是自审的盲区。判据是去数反例：这个不变量有几个写入点、几条路径，是不是每一条都成立；只覆盖了其中一条却写成全称，就是实锤。

**三、可达性对账。** 声明的每一个投递目标、每一个触发点位，端到端走一遍：真的存在能接住的那一端吗？特别留意「生产端按全集展开、消费端只有一个特例有能力」这种形状——它不报错，只会安静地永远送不到。

## 退出标准

**不是「diff 读完了」。** 是三道对账各自过完，且每条数据流的生产者—消费者—可达性都有明确结论，每条结论落在三档之一：**实锤 / 存疑 / 核实过没问题**。

在此之前不要说「没有别的问题了」。这一条是本技能存在的主要理由：漏掉的东西通常不是看不懂，是停太早。

大批量改动下「每条数据流」不是有限枚举，所以**开工时先把改动文件分成两堆，并在报告里声明这个分堆结果**：

- **机制承载**——改了行为、状态、编排、数据形状的文件。这一堆逐个走完三道对账，不许抽样
- **连锁改动**——上一堆改完之后跟着改名、跟着调整签名的文件，本身不含新决策。这一堆用抽样加全仓库死引用扫描代替逐个对账

分堆本身是个判断，会出错，所以它必须写进报告让人复核；**分错堆比漏读更危险，因为它看不出来**。任何一个文件说不清该进哪堆，就默认进第一堆。

## 项目专属探针

改动碰到左边，就去查右边。**这里只给查法，不给答案**——答案会过期，而过期的答案比没有答案更糟。

一条探针能写进这张表的判据：**它不会因为改名、新增实现或重构而变成「静默通过」。** 所以表里不出现具体标识符——一条写死名字的查法在改名之后不会报错，它照样返回一批结果，让人以为查过了。往这张表加新行时按同一条判据过一遍。

**每条探针都自带失效自检**：查法返回空、或者查出来的结构与描述对不上，说明代码结构已经变了——停下来报告这件事，不要当作通过。

| 改动碰到 | 查什么 |
|----------|--------|
| attachment | 能渲染 attachment 的执行路径现在有哪几条？逐条确认它凭什么获得这个能力——**能力只能从被调对象自己的构造参数看出来，不能从调用方传了什么参数推断**。投递端展开出的目标集合，和这份能力清单对得上吗？状态机各态由谁推进、谁回收，有没有哪个态没人管？落点：`docs/ARCHITECTURE.md`「运行时数据流」、`docs/design/loop.md` |
| prompt 注册 | 注册时能声明的字段现在有哪些、合法值各是什么？每个字段漏写会怎样——静默丢弃、兜底投出，还是抛错？投递端的过滤条件与注册端的声明对得上吗？投递端有没有单块隔离，一块炸掉会不会连累同批其余的块？落点：`docs/ARCHITECTURE.md`「Prompt 分层组合」、`docs/EXTENDING.md`「加一个 Prompt 分块」 |
| 会话落盘 | 哪些下游消费者假定落盘的 user 消息就是「用户说的话」？这次改动之后这个假定还成立吗？重建上下文的那条路径会不会把落盘内容原样重放回模型？落点：`docs/ARCHITECTURE.md`「数据与持久化」 |

`CLAUDE.md`「反直觉陷阱」一节（`**kwargs` 契约、三套自动发现深度、敏感目录）已经在会话里，本技能不复述。

本技能范围内**不跑任何验证**——跑不跑、怎么跑由用户在拍板之后决定，届时走 `$alear030-verify`。review 阶段拿不准的一律记成「存疑」，不要为了确认而自己开跑。

## 产出与分流

1. **先汇总成一份清单交用户拍板，绝不先斩后奏。** 分三级：实锤（建议处理）/ 低风险（提请注意）/ 核实过没问题（简要带过——这一档不能省，它是整份清单可信度的来源）。
2. 有「merge 前必须拍板」的项就单独拎到最前面，不要混在清单里。
3. 拍板之后才分流，三个去处：
   - **PR 顶层 comment**：讲全貌，每条给 `文件:行号` 和修法方向
   - **issue**：走 `$alear030-issue-mark`，**按主题聚合**，不要一题一条碎 issue
   - **仅汇报，不落盘**
4. 归类用复盘那三种：边界类（`tech-debt` + `boundary-violation`）/ 构造顺序类（`tech-debt`）/ 验证类（`eval-require`）。

## 操作坑（PowerShell + gh）

- **中文评论必须走文件**：`gh api repos/<owner>/<repo>/issues/<n>/comments -F body=@<文件>`。用 `-f body=$变量` 会把 UTF-8 打碎成乱码。issue 正文同理用 `--body-file`。
- **发完回读 `.body` 验证中文**，不要假定发成功了。
- 顶层 issue comment 删得掉（`DELETE issues/comments/:id`）；已提交的 review body 删不掉（non-pending 返回 422）。所以宁可发顶层 comment。
- 行内 review comment 只能落在 diff 的变更行上。
- 没有 `sed`；管道截断用 `Select-Object -First N`；`gh api graphql` 的内嵌双引号会被 PowerShell 弄坏，必须 `-f key=value` 传参。
- 评论和 issue 都进公开仓库：不留本机绝对路径、内部语境或协作过程叙述。

## 什么不走本技能

- 文档与代码的日常漂移体检 → `$alear030-doc-drift-check`
- 单个 issue 修完之后的自查 → `$alear030-issue-fix` 第 6 步（那是「改完自查」，口径是本次改动范围内的正确性；本技能是「整批 merge 前审查」，口径是机制收口）
- push、开 PR、合并 → `$alear030-push-merge`
- issue 的标签与正文格式 → `$alear030-issue-mark`
