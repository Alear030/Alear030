# Alear030 commit message 生成

这个项目的 commit message 记录的不只是"改了什么",还承担着开发日志的作用——`YYYYMMDD_HHMMSS` 前缀让 commit 本身可以按时间线回溯,"后续计划"字段让下一次打开项目的人（包括未来的你自己）能立刻知道接下来该干什么,不用去猜。所以格式要求比一般项目严格,照抄格式就行,不要自由发挥。

## 生成前先做的事

1. 跑 `git status` 和 `git diff --staged`（如果还没 add,先看 `git diff`）,确认这次改动实际涉及哪些文件。
2. 只针对**与本次任务直接相关**的文件生成 message 和执行 add。如果工作区里还有别的不相关改动（用户在做别的事、临时调试残留等）,不要一起 commit——先问用户,或者只 add 相关文件。
3. 跑 `git log -3` 看看最近几条 commit,校对一下格式手感和用词习惯（比如这个项目喜欢用"→""及"这类连接词,长句用中文顿号"、"分隔多个并列点）。

## Message 格式

**标题一行,空行,然后正文。** 这一点是硬要求:git 把第一行当 subject,其余当 body。
早期这个项目把全部内容挤在一行,结果整条两千字的 message 都成了标题——
`git log --oneline` 撑满终端没法扫,GitHub 提交列表和 blame 悬浮提示全是截断的一坨,
恰好把时间戳前缀本该提供的「按时间线回溯」能力废掉了。信息密度不用降,分开排就行。

```
YYYYMMDD_HHMMSS <一句话主题>

当前进度:
- <改动点一>
- <改动点二>

后续计划:<下一步打算做什么>
```

- **时间戳**：取当前提交时刻的本机时间,格式 `YYYYMMDD_HHMMSS`(和这个项目 session_id
  的生成规则一致)。不要用 commit 默认的 author 时间字符串,自己算出这串数字拼在最前面。
- **标题**：时间戳之后一句话概括本次主题,**控制在 50 字以内**,不写句号。
  它要能在 `git log --oneline` 里独立成立——只看这一行就知道这次干了什么。
- **当前进度**：具体说改了什么、为什么改、解决了什么问题。这个项目的风格是信息密度高、
  不说空话——不写"优化了代码",而是写清楚"重写XX提示词——以YY为核心锚点替换原Z规则"
  这种具体到"改的是什么、换成了什么"的程度。改动点多就用 `-` 列表逐条写,
  一个改动点内部的几个层面用"、"或"——"连接。**正文长度不设上限**,该写多细写多细。
- **后续计划**：下一步打算做什么。哪怕当下没有明确的下一步,也要用一句话占位
  (比如"继续推进XX主线"),**不能省略这个字段**——这是留给未来自己的路标。
- 中文标点,不加英文句号结尾。

## 记改动本身,不记改动是怎么做出来的

commit 的作者署名是项目作者本人,不是 AI。message 里不要出现协作编排的叙述——
**「派了三个子代理体检」「我逐条核实过」「先探索再规划」这类是生产过程,不是改动内容。**
读者(包括未来的你自己)要知道的是"改了什么、为什么、有什么证据",不是"这是怎么被做出来的"。

分界线是**记录发现与证据,不记录编排**：

- ❌ `三路子代理体检后逐条回文件核实再改;alear030-changelog-refresh 示例区块漂移`
- ✅ `alear030-changelog-refresh 的示例区块与正式 CHANGELOG 已漂移(逐条核对确认)`

后者保留了"核对过"这个证据,去掉了"谁核对的、用什么方式核对"。

仓库已经公开,message 会被陌生人读到,这条同时也是可读性要求。

## 生成方式

多行 message 用 `git commit -F -` 配 heredoc 传入,避免括号、顿号、代码片段
被 shell 转义搞坏:

```bash
git commit -F - <<'EOF'
20260706_143000 <一句话主题>

当前进度:
- ...

后续计划:...
EOF
```

commit 完之后跑 `git log -1` 确认正文完整,再跑 `git log --oneline -3`
确认标题行长度合适、单独看得懂。


## 边界情况

- 如果这次改动确实很琐碎（比如只改了个 typo）,"当前进度"可以写得短,但"后续计划"字段依然不能省。
- 如果用户明确要求不用这个格式（比如临时想用英文/conventional commits）,尊重用户的临时指令,不要强套。
- 不确定这次改动算不算"相关"时,列出候选文件问用户,不要自己判断着 add 进去。

## 衔接 alear030-changelog-refresh

本 commit 的“当前进度”是 alear030-changelog-refresh skill 归纳版本块的素材来源。写清楚改了什么、为什么改，积累一批同主题 commit 后用 alear030-changelog-refresh 刷新 CHANGELOG。单次 commit 不等于一个版本块，不要每次 commit 都刷 changelog。

## 衔接 alear030-push-merge

**本技能的职责到 commit 为止**——生成 message、暂存相关文件、提交,不做 push、不开 PR、不合并、不删分支。

commit 完之后如果要把分支发出去,走 `alear030-push-merge`:第一段 push + 开 PR 后停下交回用户,
放行后第二段合并并清理分支/worktree、同步本地 master。那边写死了常驻分支名单(`master` / `Alear030_dev` 永不删除),
也定了这个项目走 GitHub PR 而不是本地 merge。

两个技能分开的理由是**留一个复查窗口**:commit 之后、发出去之前,通常还要再读一遍改动。
把 push 和 merge 并进"commit一下"会让这个窗口消失,而合并进 master 之后再改就得多绕一圈。
