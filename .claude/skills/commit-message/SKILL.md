# Alear030 commit message 生成

这个项目的 commit message 记录的不只是"改了什么",还承担着开发日志的作用——`YYYYMMDD_HHMMSS` 前缀让 commit 本身可以按时间线回溯,"后续计划"字段让下一次打开项目的人（包括未来的你自己）能立刻知道接下来该干什么,不用去猜。所以格式要求比一般项目严格,照抄格式就行,不要自由发挥。

## 生成前先做的事

1. 跑 `git status` 和 `git diff --staged`（如果还没 add,先看 `git diff`）,确认这次改动实际涉及哪些文件。
2. 只针对**与本次任务直接相关**的文件生成 message 和执行 add。如果工作区里还有别的不相关改动（用户在做别的事、临时调试残留等）,不要一起 commit——先问用户,或者只 add 相关文件。
3. 跑 `git log -3` 看看最近几条 commit,校对一下格式手感和用词习惯（比如这个项目喜欢用"→""及"这类连接词,长句用中文顿号"、"分隔多个并列点）。

## Message 格式

```
YYYYMMDD_HHMMSS 当前进度:<这次改了什么>;后续计划:<下一步打算做什么>
```

- **时间戳**：取当前提交时刻的本机时间,格式 `YYYYMMDD_HHMMSS`（年月日_时分秒,和这个项目 session_id 的生成规则一致）。不要用 commit 里默认的 author 时间字符串,自己算出这串数字拼在最前面。
- **当前进度**：具体说改了什么、为什么改、解决了什么问题。这个项目的风格是信息密度高、不说空话——比如不写"优化了代码",而是写清楚"重写XX提示词——以YY为核心锚点替换原Z规则"这种具体到"改的是什么、换成了什么"的程度。多个改动点之间用"、"或者用"；"分隔（看这次改动的颗粒度,几个独立小修复用"；"分开,一个大改动内部的几个层面用"、"或"——"连接）。
- **后续计划**：下一步打算做什么。哪怕当下没有明确的下一步,也要用一句话占位（比如"继续推进XX主线"），**不能省略这个字段**——这是留给未来自己的路标,省略了下次回来就要重新翻代码猜进度。
- 中文标点,不加英文句号结尾。

## 真实例子（照着这个语感写）

```
20260705_204500 当前进度:重写slice_agent提示词——以"自包含最小单元"为核心锚点替换原单向防过拆规则,补上防过合的反向约束和信息密度划边界信号,key_words从固定3-5个改为随信息量自适应的密度原则;修复session_core两处:切片输出补markdown去壳(防模型裹```json致json.loads崩溃)、切片输入放开tool_calls/tool_result过滤(全量带工具信息供切片判边界及下游消费端提炼task);实测原8-20一坨病症根治、格式崩溃修复,字符硬截断经5次测试证伪已回退;后续计划:推进memory消费端(slice分类/task提炼)链路
```

```
20260704_225602 当前进度:README同步hook解耦后的目录结构(plan_hook替换为pre_toolUse/inject_import_args)及设计决策描述;CLAUDE.md不纳入版本控制,已在工作区同步但不提交;后续计划:继续优化整体架构代码,推进memory系统主线
```

可以看到:改动大就把每个模块改了什么点清楚,改动小也不敷衍成一句"修复bug",而是说清楚修的是哪两处、怎么修的。

## 生成方式

用 heredoc 传给 `git commit -m`,避免多行内容和特殊字符（这个项目的 message 里经常带括号、顿号、代码片段）被 shell 转义搞坏:

```bash
git commit -m "$(cat <<'EOF'
20260706_143000 当前进度:...;后续计划:...
EOF
)"
```

commit 完之后跑 `git log -1` 确认格式落地正确,尤其检查时间戳和标点有没有被意外转义。

## 边界情况

- 如果这次改动确实很琐碎（比如只改了个 typo）,"当前进度"可以写得短,但"后续计划"字段依然不能省。
- 如果用户明确要求不用这个格式（比如临时想用英文/conventional commits）,尊重用户的临时指令,不要强套。
- 不确定这次改动算不算"相关"时,列出候选文件问用户,不要自己判断着 add 进去。

## 衔接 changelog-refresh

本 commit 的“当前进度”是 changelog-refresh skill 归纳版本块的素材来源。写清楚改了什么、为什么改，积累一批同主题 commit 后用 changelog-refresh 刷新 CHANGELOG。单次 commit 不等于一个版本块，不要每次 commit 都刷 changelog。
