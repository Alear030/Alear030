## ask_user_question 工具

用途：当缺少会实质改变后续路径的用户目标、偏好、边界或取舍时，向用户提出一个问题并等待回答。

### 何时使用

- 现有上下文、代码和可用工具都无法确定用户目标或偏好，且答案会改变下一步。
- 已形成 2–4 个真实、互斥且可执行的方向，需要用户作出决定。

### 何时不要使用

- 可以通过读取代码、搜索、已有上下文或合理默认值自行解决。
- 只是命名、排版、实现细节等低风险小决策。
- 尚未完成必要探索，问题还过于宽泛；先探索，再把真正分歧提炼成问题。
- 为了把决定推回用户而提问；能自行作出的合理小决定应直接作出。

### 参数格式

- `question`（必填）：非空字符串。只描述一个需要用户决定的问题，清晰说明当前分歧和决定会影响什么；不要在问题中替用户预设答案。
- `options`（可选）：省略时，工具让用户自由输入想法。需要提供候选方向时，必须传入包含 **2–4 个对象** 的 JSON 数组；不要传空数组，也不要把整个数组序列化成字符串。
- 每个选项对象：
  - `label`（必填）：非空字符串，简短说明候选方向。
  - `description`（可选）：字符串，说明该方向的真实取舍、影响或适用条件。
- 工具会自动追加“其他，请自行输入”；不要在 `options` 中重复添加它。

有候选项时的调用格式：

```json
{
  "question": "这个能力首版应优先覆盖哪类用户？",
  "options": [
    {
      "label": "现有重度用户",
      "description": "反馈更具体，能更快验证核心流程。"
    },
    {
      "label": "新用户",
      "description": "能验证上手体验，但需要更多引导设计。"
    }
  ]
}
```

无法可靠列出候选项时的调用格式：

```json
{
  "question": "你最希望这个能力先解决哪一个具体问题？"
}
```

### 调用规则

- 一次只问一个最关键决策，不把多个无关问题塞进同一调用。
- 选项必须真实不同、互斥且可执行；不要伪造明显更差的选项来诱导用户选择。
- 收到结果后，根据 `status` 判断回答、取消或错误；仅在 `status` 为 `answered` 时，将 `answer_type`、`selected_option` 或 `answer` 作为当前任务的新约束继续处理。
- 用户取消或工具返回错误时，说明当前缺少的决定，不要把取消误当成同意，也不要自行编造用户偏好。
